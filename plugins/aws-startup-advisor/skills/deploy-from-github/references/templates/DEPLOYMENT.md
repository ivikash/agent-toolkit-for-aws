## Shape

| Event | What happens |
|---|---|
| Pull request into `main` | `.github/workflows/ci.yml`: lint, test, build without publishing, `terraform plan` for staging |
| Push to `main` | `.github/workflows/deploy.yml`: build the artifact once, deploy **staging** to every Region in parallel, health check and alarm bake in each |
| Push a tag `v*` | `.github/workflows/deploy.yml`: confirm the commit's artifact exists, deploy **production** one Region at a time, 300-second bake between Regions |
| Manual (`gh workflow run deploy.yml --ref <ref> -f stage=<stage>`) | Re-run either stage at any ref. This is also rollback. |

## Releasing to production

```sh
git tag v1.4.0
git push origin v1.4.0
# or
gh release create v1.4.0 --generate-notes
```

A tag is the production gate. The production IAM role trusts only `refs/tags/v*`, so nothing else
can deploy there. Tag only commits on `main` whose staging deploy has finished, or the run stops at
`check-artifact` with "artifact not found".

{{GATE: on a public repository or GitHub Enterprise: "The `production` environment requires a
reviewer. The run waits in the Actions tab until one of {{REVIEWERS}} approves." Otherwise: "GitHub
cannot require a reviewer on this plan for a private repository, so creating the tag is the
approval. Protect `v*` tags in the repository rules so only maintainers can create them."}}

## Rolling back

```sh
gh workflow run deploy.yml --ref v1.3.2 -f stage=production
```

The previous tag's artifact is still in ECR (newest 50 kept) or the artifact bucket (90 days), and
the rollout bakes exactly like a forward deploy. Database migrations and other one-way changes are
not undone by a rollback.

## How a deploy knows it worked

After each deploy, `scripts/ci/verify-deploy.sh`:

1. Polls `{{HEALTH_URL_TEMPLATE}}` (with the stage and Region filled in) until it returns 200.
2. Watches every CloudWatch alarm named `{{APP_NAME}}-<stage>-<region>-*` for the bake window. Any
   alarm in `ALARM` fails the deploy, which in production stops the remaining Regions.

Alarms with that prefix are what make the bake meaningful. Without them the deploy passes with a
warning.

## Where configuration lives

Repository variables (Settings, Secrets and variables, Actions, Variables), none secret:
`APP_NAME`, `DEPLOY_TARGET`, `REGIONS`, `PRIMARY_REGION`, `TF_DIR`, `AWS_ROLE_ARN_PLAN`,
`AWS_ROLE_ARN_STAGING`, `AWS_ROLE_ARN_PRODUCTION`, `TF_STATE_BUCKET_STAGING`,
`TF_STATE_BUCKET_PRODUCTION`, `ECR_REPOSITORY`, `ARTIFACT_BUCKET`, `HEALTH_URL_TEMPLATE`
(and `LAMBDA_HANDLER`, `LAMBDA_RUNTIME` for the lambda target).

`scripts/ci/set-github-variables.sh` writes them from the bootstrap outputs.

## How GitHub signs in to AWS

OpenID Connect. No access keys exist. Each stage has one IAM role that trusts one subject:

```
repo:{{OWNER}}/{{REPO}}:environment:staging:ref:refs/heads/main        -> {{APP_NAME}}-staging-github-deploy
repo:{{OWNER}}/{{REPO}}:environment:production:ref:refs/tags/v*        -> {{APP_NAME}}-production-github-deploy
repo:{{OWNER}}/{{REPO}}:environment:plan:ref:refs/pull/*/merge         -> {{APP_NAME}}-staging-github-plan (read-only)
```

The roles, the OIDC provider, the Terraform state buckets and the artifact store are created by
`infra/bootstrap/`, applied once per account by a person with administrator access. If a workflow
fails with `Not authorized to perform sts:AssumeRoleWithWebIdentity`, the subject GitHub sent does
not match a trust policy. The `deploy-from-github` skill's `verifying.md` shows how to print the
subject.

## Changing the pipeline

- **Add a Region:** add it to the `REGIONS` variable, add a provider block and an `ecr_<region>`
  module to `infra/bootstrap/` in the staging account and re-apply, push a commit to `main` so the
  build publishes to the new Region, then tag.
- **Change how the project builds or tests:** edit the three `project_*` functions at the top of
  `scripts/ci/build.sh`. Leave the publishing contract below them alone.
- **Change the bake window:** `BAKE_SECONDS` in `.github/workflows/deploy-stage.yml`.
- **Update a pinned action:** every `uses:` is pinned to a commit SHA with the tag in a trailing
  comment. Change both together.

Files that are not committed: `.bootstrap-staging.json`, `.bootstrap-production.json`,
`infra/bootstrap/terraform.tfstate*`, `infra/bootstrap/terraform.tfstate.d/`. They are in
`.gitignore`.
